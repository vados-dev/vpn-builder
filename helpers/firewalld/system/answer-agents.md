## Вопрос

**Так, не уводи меня в сторону, службы не трогаем, там и так всё уже есть по минимуму. Нужно убрать тупую проверку 0 или 1 из ok. Смотри, все команды проходят путь лежащий через другие функции. Наше дело поймать вызов Ok() и уже при обращении к ней (а это всегда в конце, т.к. она даёт результат), передать ей "да" или "нет". Например: "run_cmd $fwctl_exec enable $fw_service && ok "Служба включена" || ok "Ошибка enable" ;;"  -- Что здесь будет происходить? Мы примерно знаем какие могут быть ответы, но ok() у нас жёсткий чувак, ему сопли не нужны. Поэтому мы просто дадим окею поводов удивиться, если вывод неоднозначный, пишем его как есть под значком warn например, а выводит его уже какой-нить amswer_box. Это по простому пока, этого достаточно. Когда буду автоматизировать дальше, нужна будет база ответов и ключевые слова для поиска по ней. Да и окея будет мало, вот думаю, может сразу окею дать третью вилку, когда он не получил "да" или "нет", а третий вариант, вывод в терминал если есть, с запростом подтверждения или отмены, а если терминала нет, запрос в телеграм и там ждёт ответа в зависимости от глобальной переменной.**


```
Разобрал пример по шагам — тут красиво ложится самообнаружение статуса: ok сама ловит $? в момент вызова, ей ничего передавать не надо. Разбор вашей строки run_cmd $fwctl_exec enable $fw_service && ok "Служба включена" || ok "Ошибка enable":

1. run_cmd выполняет enable и возвращает его rc (через прозрачный  exec, без захвата — службу не трогаем).
2. rc=0 → срабатывает первый ok; внутри ok $? в этот момент ещё держит rc enable — функция вызывается, но её тело не исполнялось, значит первый же оператор видит код команды. Ловим: local rc=$? — и это первый оператор в теле, до всяких local out=....
3.  rc≠0 → && проваливается, срабатывает второй ok — и в нём $? тот же самый код enable. Обе ветки дают окейправду автоматически.
4. Неоднозначный вывод (судила overlay_cmd, поставила AMBIG=1) → ok разворачивает третью вилку: не решает сама, а отдаёт «как есть» под ⚡ в answer_box.
```

Одна строка в судье — откуда берётся «удивление» (AMBIG), в существующую overlay_cmd, в начало проверки:
```
    overlay_cmd(){ local out rc; out="$("$@")"; rc=$?; if [ "$rc" -eq 0 ] && [ -n "$out" ] && [[ "$out" =~ (${OK_PAT:-success|ok|done|active}) ]] && ! [[ "$out" =~ (${FAIL_PAT:-error|fail|denied|refused}) ]]; then AMBIG=0; elif [ "$rc" -ne 0 ] || [[ "$out" =~ (${FAIL_PAT:-error|fail|denied|refused}) ]]; then AMBIG=0; else AMBIG=1; fi; return "$rc"; }
```
### :warning:**Что тут важно знать**

:exclamation:**local rc="$?" первым оператором — не local rc="$?" x="y" и не после других команд, иначе $? уйдёт. Это контракт ok: «стою сразу за командой».**

:exclamation:**return "$rc" из ok — якорь не рвёт цепочку: ok "..." || { err "..."; exit 2; } работает, если понадобится добить жёстко.
AMBIG — глобал, судья его ставит, ok потребляет и сбрасывает. Один сигнал на один вызов; если забудете сбросить где-то в обход ok — следующий вызов окей удивится повторно, поэтому сброс живёт в самой ok.
answer_box теперь минимальна: только формат ⚡. Смысл («что это было») ей приносит текст от ok. Когда дойдёт до базы ответов — она станет местом, где будет разбираться конкретика.**

:exclamation:**tg_ask — честная заглушка: сообщение шлёт, ответ НЕ ждёт, умирает с явным текстом. Цикл getUpdates с offset и таймаутом — следующий шаг, когда определитесь с TG_CONFIRM (например: 1 — всегда ждать, 0 — считать подтверждением сам факт отправки).**
